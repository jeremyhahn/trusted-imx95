## Purpose

trusted-imx95 is the device repository for the NXP FRDM-IMX95-PRO, at Layer 0 as a device repository: the board's firmware, its Linux image, its secure world and its secure key handling live here.
The board is the i.MX 95 with six Cortex-A55, one Cortex-M33, one Cortex-M7, the EdgeLock secure enclave and the NPU (UM12527 §1.2, §2.1); it is the first HSM device of the portfolio.
go-xkms defines the device's wire protocol and runs xkmsd on its Linux side; go-trusted-platform provisions, enrolls and attests the device and its image.
It stays the platform image: there is no `trusted-firmware-imx95` repository, and other HSM devices live in trusted-firmware or a `trusted-firmware-<application>` repository.
Every design and change about the hardware cites a document and section in [references/](references/README.md); a fact the documents do not give is reported as missing, never guessed.

## Boundaries

- Owns the FRDM-IMX95-PRO platform image: the Linux image, its boot container and the System Manager configuration.
- Owns the device side of go-xkms's `hsm-device-protocol` and of go-trusted-platform's `hsm-device-lifecycle`.
- Never defines the wire protocol and never implements xkmsd: go-xkms owns both and runs xkmsd on the board's Linux side.
- Never owns device enrollment, the device registry, fleet policy or attestation verification: go-trusted-platform and go-xkms own them.
- The Cortex-M7 firmware: trusted-firmware's `imx95` row (trusted-firmware #49, closed 2026-10-25) holds the M7 firmware core and its `frdm-imx95-m7` board profile, on its `cortex-m` port. Owner ruling 771 keeps trusted-firmware as the Cortex-M (TrustZone-M) product, which on the i.MX 95 is the M7.
- The Cortex-A55 secure world is upstream TF-A and the NXP BSP's OP-TEE, configured and built here; this repository writes no TF-A or OP-TEE OS code of its own (owner ruling 771, `secure-world` row).
- Never replaces NXP's System Manager on the Cortex-M33: the System Manager stays NXP's, and this repository holds only its configuration.
- The board's image is built here, never by go-trusted-platform's image pipeline.
- The CompuLab UCM-iMX95 material in [references/](references/README.md) and `resources/` is reference only; it is not the device.

| secure-world | planned | The board's Cortex-A55 secure world, as owner ruling 771 sets it: upstream Arm Trusted Firmware-A (BL31) and OP-TEE OS from NXP's Linux BSP, on the FRDM-IMX95-PRO. Per owner ruling 771, BL31 is upstream Arm TF-A at a tagged upstream release with i.MX 95 platform support (currently v2.15.0, pinned in `secure-world/bsp.lock`), not NXP's `imx-atf` fork; OP-TEE OS is NXP's BSP OP-TEE at the revision one named NXP Linux BSP release carries, and that BSP release is provisional until the owner chooses the baseline (#14). It is not this repository's own secure-world code: this repository configures and reproducibly builds it, and its images go into the boot container. OP-TEE runs the PKCS#11 TA, which go-xkms's PKCS#11 backend uses, and hosts the firmware TPM TA, which the `ftpm` row owns with its kernel driver, NV storage, EK and measured boot; any custom TA is reached through `/dev/tee0`. go-trusted-platform and go-xkms run in Linux and use TrustZone only through OP-TEE. Keys these TAs hold sit in OP-TEE's storage, not in the enclave: the `secure-key-handling` row's requirement that the board's keys stay in the enclave's key store is unchanged. The Cortex-M7 stays trusted-firmware's Cortex-M (TrustZone-M) product, the Cortex-M33 stays NXP's System Manager, and the EdgeLock secure enclave is the hardware root. No document in [references/](references/README.md) gives the i.MX 95's TrustZone configuration; the one that does is missing. | [secure-world/](secure-world/architecture.md) |
| ftpm | planned | The board's firmware TPM 2.0, as owner ruling 927 sets it, so that the board is provisioned like any other system through go-xkms's existing TPM 2.0 workflows: endorse-01, then enroll-01, then device-attest-01 in the `tpm` format. Per the ruling, today's image has no firmware TPM: the kernel's `CONFIG_TCG_FTPM_TEE` is off and the BSP's OP-TEE (4.10, as the ruling reports it) carries the PKCS#11 TA only. `secure-world` provides OP-TEE; this row owns: the OP-TEE fTPM TA, built on Microsoft's TPM 2.0 reference implementation (`ms-tpm-20-ref`) into OP-TEE as an early TA, at a source revision to be pinned; the Linux `tpm_ftpm_tee` driver (`CONFIG_TCG_FTPM_TEE`), with `/dev/tpmrm0` present at boot; the TPM's persistent NV in OP-TEE secure storage: on production devices in the eMMC's RPMB, written only after OEM close (owner ruling 1234), and on development boards only in the REE file system (the root file system), which gives no rollback protection and is wiped with the root file system (owner ruling 1234); an endorsement key created on first boot, which has no manufacturer certificate, so go-xkms endorse-01 issues its certificate before enroll-01, and only after an EdgeLock enclave attestation (owner ruling 1234); and measured boot into the fTPM's PCRs where the boot chain supports it, with every stage that cannot extend listed as a gap. The EK and any attestation key are fTPM keys in OP-TEE's storage, the device's TPM identity, not the board's keys of the `secure-key-handling` row, whose requirement that those stay in the enclave's key store is unchanged. Programming the RPMB key is a one-time, irreversible eMMC step of the same class as a fuse burn, taken after OEM close by the provisioning station (owner ruling 1234); nothing in this repository performs or scripts it. | [ftpm/](ftpm/README.md) |
| secure-key-handling | planned | The board's keys are generated and held in the EdgeLock secure enclave's key store and never leave it in the clear, as trusted-firmware's `imx95` row requires of the key tier (RM00284 §2.4, §3.2). A key update or a key deletion counts as rollback-protected only when the enclave acknowledges both the strict-operation flag and the monotonic-counter flag for that operation; an operation acknowledged with only one of them is not rollback-protected (RM00284 §2.4.2; owner decision 241). Signing, data storage and attestation use the enclave's HSM API (RM00284 §3.4, §3.8, §3.12); the Generic Crypto APIs are not available on the i.MX 95 (RM00284 §3.45). Which side calls the HSM API, the Cortex-A55 Linux side or the Cortex-M7, is an open question for the owner. The board also carries an NXP SE051 secure element (U28, on I2C2 at 0x48, with the J4 control header; UM12527 §1.1, §1.5 Table 3, §2.5 Table 9). Whether it holds any key, and its role beside the enclave, is an open question for the owner; its documentation is not in [references/](references/README.md) and is listed as missing. | [secure-key-handling/](secure-key-handling/architecture.md) |
| oem-key-provisioning | planned | Provisions the OEM keys into the enclave through the vendor's flow: key exchange, then the import of the wrapped key (AN14861 §2, §5.2, §5.3; RM00284 §3.20, §3.2.6.3). The device's life cycle moves from OEM open to OEM closed through the enclave (RM00284 §3.23), and the monotonic counter fuses are configured once (RM00284 §3.24). AN14861 is written for the RT1180; the i.MX 95 fuse map and life-cycle effects come from IMX95RM and the i.MX 95 Security Reference Manual, both missing. When the life cycle is closed, and where provisioning runs, are open questions for the owner. | [oem-key-provisioning/architecture.md](oem-key-provisioning/architecture.md) |
| hsm-device-protocol | planned | The device side of go-xkms's `hsm-device-protocol`, which go-xkms defines, between xkmsd and the board. The network transports are the board's two 1 GbE ports and a 10 GbE expansion card on the Slim-SAS connector (UM12527 §1.2 Table 1, §2.18). The 10 GbE expansion card is not in the board kit and its documentation is missing. The direct-attach transport and the network protocol surface are go-xkms's open questions (go-xkms #1521), in the owner queue as item 160; no device-side requirement is written here before the owner answers (Software Department ruling 195). | none |
| device-lifecycle | planned | The device side of go-trusted-platform's `hsm-device-lifecycle`: the board is provisioned, enrolled and attested, and its image attested, by go-trusted-platform's control plane, which builds no firmware for it. The enclave offers device attestation (RM00284 §3.12). Owner ruling 927 has the device attest through its firmware TPM with go-xkms's device-attest-01 in the `tpm` format (`ftpm` row); what further evidence the device presents, and the root it chains to, are not decided here, and are an open question for the owner. | none |
| hsm-self-defence | planned | The HSM device side of the tamper response that trusted-firmware's `hsm-self-defence` row enforces on the Cortex-M7 and go-xkms's `hsm-self-defence` row names. The M7 acts through NXP's System Manager, whose configuration is this repository's (`system-manager-config`), and the EdgeLock secure enclave: power domains, PHYs, key zeroisation and shutdown. Whether the Cortex-A55 tamper detector, the NPU model and the IMA log are built in this repository is not decided, and is an open question for the owner. No document in [references/](references/README.md) gives the EdgeLock tamper pins; the one that does is missing. | none |

## Interfaces

- No interface is built yet; nothing in this repository is code.
- The device side of go-xkms's `hsm-device-protocol`, over the board's 1 GbE ports and the 10 GbE Slim-SAS connector (UM12527 §2.18).
- The signed boot container on the default boot device, the eMMC (UM12527 §2.3).
- Board interfaces: the SW4 boot modes and the USB serial downloader (UM12527 §2.3); the per-core debug UARTs on J22, whose port mapping is not fixed (UM12527 §2.19).
- Vendor documents and what each is read for: [references/README.md](references/README.md).

## Release criteria

- `docs/SPEC.md` and `ROADMAP.md` exist in the handbook's shapes and agree.
- The owner approves the whole of both files.
- CI conforms to the handbook's `software/conventions/ci-standard.md`: build, unit tests, integration tests, security scans and the latest-version check, all in the project's devcontainer image.
- The firmware split follows owner ruling 771: the Cortex-A55 secure world is upstream TF-A and the NXP BSP's OP-TEE, built here; trusted-firmware's `imx95` row owns the Cortex-M7 firmware and its board profile; the Cortex-M33 stays NXP's System Manager.
- BL31 is pinned to a tagged upstream Arm TF-A release (owner ruling 771), and OP-TEE OS to the revision one named NXP Linux BSP release carries, that BSP release provisional until the owner chooses the baseline (#14) (`secure-world` row).
- The `ftpm` row's fTPM TA source revision is pinned, and the open questions in [ftpm/](ftpm/README.md#open-questions-for-the-owner) are answered, the RPMB key question first.
- The owner decides how the platform image is built; the CompuLab Yocto image is reference only.
- The open questions in the Features rows are answered: the side that calls the HSM API, the SE051's role, the provisioning place and life-cycle close, the attestation evidence beyond the firmware TPM's `tpm`-format device-attest-01 (`ftpm` row), and the A55 side of `hsm-self-defence`.
- IMX95RM, the i.MX 95 Security Reference Manual, the System Manager documentation, the NXP Linux BSP documentation, the SE051 documentation and the 10 GbE expansion card documentation are in [references/](references/README.md).
- A milestone and one issue for each feature row exist in this repository.
