# Plan 159: adopt handbook ci.yml v1.54

## Objective
Replace `.github/workflows/ci.yml` (v1.35.2 plus the hosted-runner change of
#148) with the handbook template v1.54 (handbook commit 1ad68ab8, balanced
runner pools, ruling 1137), keeping this repository's CUSTOMIZE values. One
ci-config PR; no Codex round (ruling 443).

## CUSTOMIZE values carried over

  workflow `env`.
- `COVERAGE_THRESHOLD: 90`, `GO_BUILD_TAGS: ""`, `DOCS_ONLY_PATTERN`,
  `LINT_GATES_PATTERN: '.'`, `RELEASABILITY_TEST: ""`, `OBJSTORE_SEAMS: ''`
  and the nightly cron `0 4 * * *`: equal to the template's defaults.
- Job timeouts and soak values: the template's (60, 30, 90, 45, 60, 90;
  `SOAK_MINUTES: 30`, `SOAK_TARGET: integration-test`, `IN_IMAGE_NETWORK: none`).
- `make gosec` in `lint` runs on a docs-only PR too (the CST guard and the tree
  secret scan).
- Jobs `history-scan`, `system-manager-build` (runner of the template's `lint`
  class) and `releasability` (the template's `ci-gate` class), with their CI
  Gate `needs` and `check` lines; `history-scan` and `releasability` are class
  `always`, which the gate's `check()` never accepts skipped.
- `deps-check` and the release fetch (#144) stay in `lint`: v1.42 moved them to
  `scans.yml`, which this repository does not have.
- Image-ID pinning: `make toolchain-ref` supplies `TOOLCHAIN_IMAGE` in three
  jobs, and the integration and soak `make` lines pass `IT_IMAGE_ID` from
  `IT_LEASE_ID`. The env-file loops copy `GOPRIVATE` only, never
  `GIT_CONFIG_*`.
- No private-pattern step in `lint`: the pull_request workflow names no
  private-pattern secret.
- `make security` and `trivy image (integration image)` stay in the image job
  on the full tier; the template moved them to `scans.yml`, which this
  repository does not have.
- The CI Gate `check()` has a class `always` besides the template's.
- Scripts: `scripts/ci-mask-lan.sh`, `ci-image-history.sh` and
  `assert-build-tags.sh` are copied unchanged from handbook commit 1ad68ab8,
  with the template's tests under `test/testdata/`, run by
  `test/ci_helpers_test.sh`. The ci-image-history test needs PyYAML, which
  the toolchain image lacks, so it is skipped there with a named line.
  `ci-image-cache.sh`, `in-toolchain-image.sh` and `trim-ci-caches.sh` keep
  this repository's versions, not the template's: the template's lack the
  image-ID pinning that 22 tests in `test/ci_scripts_test.sh` enforce (a push
  run refuses a tag and starts its stages by the verified image ID).
- Trusted image reference: the integration, image and soak lease blocks
  resolve the image through `make -s it-ref IT_IMAGE="$IT_IMAGE"`, as on main,
  never the `$IT_IMAGE` tag directly (on a trusted run the tag names whatever
  the daemon holds under it). A test counts three `it-ref` resolutions and no
  tag inspect.
- The image job's checkout keeps `fetch-depth: 0` (CUSTOMIZE, as on main),
  because `make security` scans every commit and a shallow checkout hides a
  credential committed and removed earlier. A test asserts it.
- The image-history suite runs in CI and is never skipped. The toolchain
  image (`build/docker/devcontainer/Dockerfile`) gains Alpine's `py3-yaml`
  in its existing `apk add` line, because the suite's wiring cases parse
  `ci.yml` with PyYAML. `test/ci_helpers_test.sh` fails when PyYAML is
  missing and `CI` or `GITHUB_ACTIONS` is `true`; elsewhere (a container
  that is not the toolchain image) it prints one `skip` line and does not
  run the suite. With PyYAML present the suite always runs and must pass.
- `test/testdata/ci-image-history-tests.py` is the template's file except
  its publish fixtures (named in its header). The template's fixtures stub
  its older publish path (`docker save`, a manifest probe, a history check
  before the push). The retained `ci-image-cache.sh` v5 takes the Dockerfile
  path from `make`, publishes with `docker buildx build --output
  type=registry`, reads digests through `docker buildx imagetools inspect`
  and runs no history check of its own, so the adapted fixtures stub that
  path and assert: login before build, the build pushes to the registry
  name, a held tag is not rebuilt, and a registry digest that is not the
  build's fails. The template's "history before push" ordering case has no
  counterpart in the retained script and is dropped.

- Departure from the template at handbook 1ad68ab8 (Codex security P1): the
  runner-label check's `||` evaluator returns "unknown" when its left operand
  is unknown, however the fallback reads. The template returned a truthy
  fallback, so `vars.RUNNER || 'ubuntu-latest'` counted as hosted although the
  variable can name bigdisk or another prohibited runner, fork pull requests
  included. The check now reads it as an unknown label and fails closed.
  `test/runner_labels_test.sh` runs the step extracted from `ci.yml` on
  fixture workflows, with the regression cases (variable, input and two
  variables ahead of a hosted fallback), and keeps a known hosted label ahead
  of a variable hosted.

- Second departure from the template at handbook 1ad68ab8 (Codex security
  P1 at verify 6): the release restriction ran on the `runs-on` source text
  only, so `runs-on: ${{ format('re{0}', 'lease') }} # self-hosted: hardware:
  <reason>` in a pull_request workflow reached the release pool: the text
  names no `release` and the waiver skipped every later check. The step now
  also evaluates the labels (`eval_release`, marked CUSTOMIZE). A runs-on
  that evaluates to `release`, or to no literal labels while a
  `# self-hosted:` comment sits on it, takes the release path, which needs an
  `if` that restricts it to the allowed events. The waiver relaxes the
  hosted/self-hosted class rule only, never the release restriction.
  `test/runner_labels_test.sh` holds the finding's case, a `format()` case
  without a waiver, a `join()` case, and a literal `release` with a waiver
  (all refused), and a literal self-hosted list with a waiver (passes).

- Third departure from the template at handbook 1ad68ab8 (three Codex
  security P1s at verify 7, all ways past the release-runner restriction
  through the step's expression simulator): a `release` job whose `if:` tests
  `github.head_ref == 'topic'` (the simulator fixes head_ref at one value); a
  list element `"${{ format('re{0}', 'lease') }}"` under a waiver (list
  elements were split on commas and never evaluated); and a
  `github.server_url == 'https://github.com' && 'ubuntu-latest' ||
  format('re{0}', 'lease')` selection (the simulator always read the server
  as github.com, which Gitea is not). The release decision no longer
  simulates. In a workflow that any trigger outside push, workflow_dispatch
  and schedule can run (or whose triggers cannot be read), a `runs-on` is
  accepted only as literal labels with no expression anywhere and none
  `release`, or as exactly one of the template's own selection expressions
  (`SELECT_OK`, copied from 1ad68ab8). A job that names `release` also needs
  an `if:` that is, whitespace-normalized, exactly one of `COND_OK`, each of
  which excludes every untrusted event. Everything else is refused, and the
  `# self-hosted:` waiver is never consulted for this decision; it relaxes
  the hosted/self-hosted class rule only, which keeps the simulator as the
  template has it. Marked CUSTOMIZE in `ci.yml`; the cases are in
  `test/runner_labels_test.sh`. The template's step needs the same change
  upstream: its simulation of the release decision has the same three holes.
  A literal expression (`${{ 'ubuntu-latest' }}`) in a pull_request workflow
  is now refused (and, from verify 8, in every workflow, see below).

- A third departure from 1ad68ab8 (resume 10; two more Codex security P1s at
  verify 8): the step read the workflows as text, so a quoted `'jobs':` or a
  flow-map `jobs: {a: {runs-on: release}}` skipped the job loop and printed
  OK; and in a workflow with only push/workflow_dispatch triggers the release
  job skipped the exact-condition allowlist and fell back to the simulation,
  so `if: github.ref == 'refs/heads/topic'` passed. The step now loads each
  workflow with PyYAML's `safe_load` (installed in the step when the runner
  lacks it, never a skip; the `on` key is read as `on` or as YAML 1.1's
  `true`). A file that does not parse, whose `jobs` is missing or not a
  mapping, or whose `runs-on` is neither a string nor a list of strings, is
  refused. The runs-on and `if:` allowlist applies to every job of every
  workflow whatever its triggers, so a `${{` runs-on passes only as one of the
  template's selection expressions and a `release` job only with one of the
  `COND_OK` conditions. The text is read only to find the `# self-hosted:`
  waiver comment on a runs-on line, and a job it cannot find there gets no
  waiver. Marked CUSTOMIZE in `ci.yml`. The template's step needs the same
  structural parse upstream: its text-line job enumeration has the same hole.

- A fourth departure from 1ad68ab8 (resume 11; Codex security P1 at verify
  9): the selection-expression exemption checked only the consumer `runs-on`
  text, so a new workflow with its own hosted `preflight` job outputting
  `"release"` reached the release pool from a pull request. The exemption now
  needs (a) the file `.github/workflows/ci.yml`, (b) every
  `needs.<job>.outputs.<name>` the expression reads to name the job
  `preflight`, with that job's parsed definition equal to a pinned SHA-256 of
  its canonical JSON (`PRODUCER_SHA256` in the step; the Runner labels step
  that holds the constant is left out of the dump, its `run` replaced by a
  marker, so the pin is not circular), and (c) the reading job to list
  `preflight` in its own `needs`. Any other workflow, or a changed producer,
  using `${{` in `runs-on` is refused, and the synthetic selection outputs
  apply to ci.yml only. Changing the preflight job means recomputing the pin.
  Marked CUSTOMIZE; the template's step needs the same pin upstream.

## Residual for Infra
A pull request can edit ci.yml and this guard itself, so the guard is defence
in depth only. The enforcing control is a release runner group restricted to
selected workflows and refs, which is Infra's to set.

## Repository variables v1.54 reads (Infra's to set)
`CI_HOSTED_SHARE`, `CI_SELF_HOSTED_BIGDISK`, `CI_SELF_HOSTED_BIGDISK_DOCKER`
and `CI_PREFLIGHT_RUNS_ON`. Until they are set the template falls back to
hosted runners with a warning.

## Out of scope
code-review.yml, signatures.yml and releasability.yml; a `scans.yml`.
