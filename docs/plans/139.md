# Plan 139: xkmsd on the board, built, deployed and burned in

Epic #139. The board must always run the latest go-xkms, and burn-in and
failure tests must find bugs that could lose data or cause critical problems
in production. Fuses, the life cycle and RPMB stay untouched.

This lane cannot reach the board. It writes the tooling and builds the
artefact; the coordinator runs the deploy and the tests on the board.

## Slices

1. Build. `scripts/xkms/xkmsd-build.sh [<commit>]` clones go-xkms (read-only,
   into the gitignored `build/go-xkms/src`), builds a static linux/arm64
   `xkmsd` and `xkmsctl` with the version set to the commit, and writes
   `build/xkms/<commit>/{xkmsd,xkmsctl,manifest.txt}`. The build date is the
   commit date, so a rebuild is byte-identical.
2. Deploy. `scripts/xkms/xkmsd-deploy.sh <ssh target> <build dir>`: preflight,
   backup with xkmsd stopped (SHA-256 list), install, health check, automatic
   restore on failure, `--rollback <stamp>`, keep the newest 5 backups.
   `test/xkms_board_tools_test.sh` runs it against a fake board (stub `ssh`,
   fake `systemctl`, fake `xkmsd`): success, failed health check with a byte
   for byte restore, `--rollback`, pruning.
3. Burn-in. `scripts/xkms/burnin/`: functional sweep, soak, durability,
   power-loss (off unless `--hard-reboot`), disk-full, concurrency,
   restart-under-load. Each has `--help` and `--dry-run`; the test file runs
   every `--dry-run`. `docs/xkms-board/burn-in.md` says what each proves.

## Out of scope

Edits to go-xkms; fuses, life cycle, RPMB; SPEC.md and ROADMAP.md; any board
address in the repository (the target is always an argument); running
anything on the board (the coordinator does).
