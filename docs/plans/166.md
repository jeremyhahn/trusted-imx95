# Plan: #166 secure-world builds twice and compares

Objective: `make secure-world` builds bl31.bin and tee.bin twice in separate clean
build directories and fails unless both are byte-identical, the way `sm-build.sh`
does, replacing the one manual match in docs/secure-world/build.md. Host side only;
the BSP stays provisional exactly as secure-world/bsp.lock says.

## Slices

1. Two builds and a comparison (host-side only).
   - scripts/secure-world-build.sh: the default run is a driver that runs the script
     twice (internal `--single`) in work/build-1 and work/build-2, compares the two
     artefacts by SHA-256, publishes only on a match (bl31.bin, tee.bin, SHA256SUMS,
     build-info.txt with the agreed hashes), and on a difference fails naming the
     artefact and both hashes. The build steps are unchanged, so the build
     configuration digest in build.md still holds.
   - test/secure_world_build_test.sh: stubbed match and difference, offline.
   - docs/secure-world/build.md: the scripted check and its output replace the
     hand match.
2. The CI build job (issue #166's title includes it): `secure-world-build` in ci.yml.
   - Runs in a python:3.13 Debian bookworm image pinned by digest: the lock's wheels are
     CPython 3.13 x86_64 glibc (manylinux_2_28, manylinux2014), which the Alpine (musl)
     toolchain image cannot install. uv is installed from a hash-pinned wheel.
   - Builds only when a changed file is under secure-world/, or is the script, its test,
     the Makefile or ci.yml; otherwise its steps are skipped, the job succeeds and the
     CI Gate counts it passed. A push or schedule always builds.
3. (Later.) Run the scripted check on the real sources and record the real hashes.
