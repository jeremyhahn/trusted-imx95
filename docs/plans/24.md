## 2026-11-24: the enclave interface trace

Read NXP linux-imx (commit 6e694eda40aabd6671fca82b5416dbd76beeebb9) and imx-secure-enclave (commit 463845060a79dd9a6d39db3b3d8dff60225b9dfd), both the peel of tag lf-6.18.37-2.1.0, the pinned BSP release. Result: `docs/hsm-device-protocol/enclave-interface-trace.md`, facts only; xkmsd-node.md §4 question 5 now points to it. The survey's own cells stay as surveyed. The docs test checks the trace (words, links, status line, a citation or `unconfirmed` in each question section, and two negative cases).

Still unconfirmed: the node's mode and owner on the image (devtmpfs and udev, not read); the messaging unit's size limit (mailbox driver); behaviour after an enclave reset (no handling found in the driver); whether the image's kernel recipe uses the commit read; the meaning of the NVM daemon's session flag; the sequence-control file `se_msg_sqfl_ctrl.c`.

Owner questions, each proposed, pending owner approval (no requirement changed):

1. R8: the trace shows one command in flight per interface, so a separate listener process and key holder share one queue at the enclave. Does that bear on the split?
2. R6: the node mode and owner come from the image's device manager, not the driver. Should the image fix the node's group and mode?
3. R11: the driver has a timeout, a busy flag and a late-response recovery but no reset handling in the code read. Does fail-closed need a reopen step?
4. The enclave-initiated command path has a 256-byte buffer, and a clamp that the next statement appears to overwrite (trace (d)). Treat as a question for NXP, not a finding.
