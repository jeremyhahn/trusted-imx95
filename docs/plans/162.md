# Plan: #162 secure-key-handling, the enclave HSM API client (Linux side, provisional)

Epic row `secure-key-handling`. Branch `row/162-skh-ele`.

## Objective

A pinned, cross-built copy of NXP's public secure-enclave user library, and a
minimal key-store client (key generate, sign, delete) whose update and delete
path reports "rollback-protected" only when the strict-operation flag and the
monotonic-counter flag are both acknowledged for that operation (owner
decision 241). The Linux A55 side calls the HSM API: this is the provisional
default. The owner question (A55 Linux or M7) stays open in the docs.

## Slices, in order (all done unless under Open items)

1. Source pin and build: `secure-key-handling/ele-lib.lock` (repository,
   commit, SHA-256 of the `git archive` tar, build platform `ele`; toolchain
   pinned in `secure-world/bsp.lock`) and `scripts/ele-lib-build.sh`
   (`--check-lock`, `--src-only`, fetch outside the tree, verify commit and
   SHA-256 fail closed, cross-build). Test: `test/ele_client_test.sh`.
2. The client and its policy check: `secure-key-handling/client/ele_client.c/.h`
   (the rollback-protected decision; generate, sign, delete over an ops
   table), `ele_stub.c/.h`, `ele_client_test.c`. Tests: both flags, strict
   only, counter only, neither; counter warning; flags for different operations.
3. Docs: `docs/secure-key-handling/client.md` (provisional), linked from
   `architecture.md`.
4. The binding to the library's real HSM API (symbols read from the public
   headers at the pinned commit): `ele_hsm_backend.c/.h`,
   `ele_hsm_consts_check.c` (`_Static_assert` of flag and return values),
   `ele_client_cli.c` with `ele_cli_args.c/.h` (nonce from a file
   descriptor, strict number parsing), `ele_hsm_fake.c/.h` (a double of
   libele_hsm), `ele_hsm_backend_test.c`, `ele_cli_args_test.c`.
   - The backend part of the test needs the fetched source (`ELE_SRC`, the
     toolchain image's `/opt/ele-src`); `REQUIRE_ELE_SRC=1` makes unset a
     failure, otherwise it prints `skip: ELE_SRC unset`.
   - Generate is refused without `--split-confirmed`; `sign` prints lowercase
     hex or raw bytes with `--raw`; the nonce sits in one mlock'd buffer, erased
     on every exit; the process is non-dumpable, RLIMIT_CORE 0; SIGPIPE ignored.
   - The counter flag is never reported acknowledged (`HSM_NO_ERROR` also
     stands for a success-tagged warning), so every key-store update (generate,
     delete) fails closed with "NOT rollback-protected" until Q2 is answered.
   - `hsm_sign` accepts only a 64-byte signature (`exp_signature_size`).
5. One child per operation (departure from the first design, which forked
   only the key-store open): the session open, the key-store open with the
   nonce, the operation and the closes all run in one forked child (non-dumpable,
   locked, `_exit`, fixed-size result over a pipe; the parent checks status and
   exact length, holds no handle, makes no vendor call). The child inherits no
   credential: the parent's copy sits in a wipe-on-fork page and is sent over a
   pipe only after the child reports it is locked. `ele_hsm_open` only locks memory and records the slot. The
   stack scrub stays as defence in depth, not claimed as erasure. Tests: all
   of an operation's vendor calls in one pid that is not the parent's; killed,
   nonzero and short child fail closed; the parent's nonce buffer is zero.
   Built and run against the pinned source (lane 162-skh-build).

## Open items

- Q2, the ELE rollback gap: owner answer pending; until then no update is
  reported rollback-protected. The sound fix for the nonce residue is a
  build-time patch of the pinned library (pinned by SHA-256), owner's decision.
- Vendor second-reader review: the claims about the response decoder
  (success-tagged warning maps to `HSM_NO_ERROR`), the signature output and
  the credential marshalling rest on the source trace in `client.md` at
  commit 463845060a79 and have had no second reader. Reproduce:
  `scripts/ele-lib-build.sh --src-only --work <dir outside the checkout>`
  (SHA-256 `ELE_ARCHIVE_SHA256` in `ele-lib.lock`). No vendor source is here.
- Board validation: none of this has run on a board.
