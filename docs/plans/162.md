# Plan: #162 secure-key-handling, the enclave HSM API client (Linux side, provisional)

Epic row `secure-key-handling`. Branch `row/162-skh-ele`.

## Objective

A pinned, cross-built copy of NXP's public secure-enclave user library, and a
minimal key-store client (key generate, sign, delete) whose update and delete
path reports "rollback-protected" only when the strict-operation flag and the
monotonic-counter flag are both acknowledged for that operation (owner
decision 241). The Linux A55 side calls the HSM API: this is the provisional
default. The owner question (A55 Linux or M7) stays open in the docs.

## Slices, in order

1. Source pin and build.
   - `secure-key-handling/ele-lib.lock`: repository, commit (the revision
     meta-freescale's `imx-secure-enclave` recipe takes from meta-imx at the
     commit `platform-image/manifest.lock` names), SHA-256 of the
     `git archive` tar, build platform `ele`. The toolchain is the pin in
     `secure-world/bsp.lock`.
   - `scripts/ele-lib-build.sh`: `--check-lock` (offline, parses and checks
     every value), otherwise fetch outside the tree, verify commit and
     SHA-256 (fail closed), cross-build for aarch64.
   - Test: `test/ele_client_test.sh` runs `--check-lock` and its failures
     (bad commit, bad digest, UNREAD, missing name, toolchain pin missing).
2. The client and its policy check.
   - `secure-key-handling/client/`: `ele_client.c/.h` (the pure
     rollback-protected decision, and generate, sign, delete over an ops
     table), `ele_stub.c/.h` (a host stub of the ops), `ele_client_test.c`.
   - Tests: both flags, strict only, counter only, neither; a counter
     warning; the two flags acknowledged for different operations.
3. Docs: `docs/secure-key-handling/client.md` (provisional), linked from
   `architecture.md`.
4. The binding (scope widened by the coordinator's resume brief 2: "bind the
   client to the pinned library's real HSM API before the verify", with the
   symbols read from the library's public headers at the pinned commit).
   - `secure-key-handling/client/`: `ele_hsm_backend.c/.h` (the ops table over
     the library's HSM calls), `ele_hsm_consts_check.c` (`_Static_assert` of
     the flag and return-code values against the headers), `ele_client_cli.c`
     with `ele_cli_args.c/.h` (the `ele_client` command; the nonce comes from
     a file descriptor, every number is parsed strictly), `ele_hsm_fake.c/.h`
     (a test double of libele_hsm), `ele_hsm_backend_test.c`,
     `ele_cli_args_test.c`.
   - `scripts/ele-lib-build.sh` cross-builds `ele_client` against the built
     `libele_hsm` (`make ele-lib`, needs the network, not in CI).
   - Tests (`test/ele_client_test.sh`): the backend's request flags and its
     translation of `HSM_NO_ERROR`, `HSM_KEY_STORE_COUNTER` and other codes
     against the double; the command line (counter warning exits nonzero,
     no nonce in argv, `del 4294967297`, `1junk`, `-1`, `''` refused before
     any HSM call). The backend part needs the fetched source (`ELE_SRC`);
     it comes from the toolchain image's `ele-src` stage (pinned by
     `ele-lib.lock`, unpacked to `/opt/ele-src`, `ENV ELE_SRC`). With it
     unset the test fails when `REQUIRE_ELE_SRC=1` (set by the toolchain
     image, so by the GitHub job that runs in it), and otherwise prints
     `skip: ELE_SRC unset`.
   - Resume 4: generate is refused before any HSM call without
     `--split-confirmed`; `sign` prints one line of lowercase hex, or raw
     bytes with `--raw`; the nonce sits in one mlock'd buffer, erased with
     the library copy on every exit, with the process non-dumpable and
     RLIMIT_CORE 0.
   - The client fails an update on a counter warning or a missing
     acknowledgement; the diagnostic state is kept.
   - The toolchain image gains `build-base` for the host C tests.
  - Resume 2 (verify-1 findings): the counter flag is never reported
    acknowledged, so generate is refused and nothing is reported
    rollback-protected from this binding (HSM_NO_ERROR also stands for a
    success-tagged warning); `ele_hsm_open` locks all memory (`mlockall`) and
    fails closed, then scrubs 16 KiB of stack after the library call on every
    exit. The scrub is best effort; the sound fix is a build-time patch of the
    pinned library, pinned by SHA-256, the owner's decision, not done. Residual
    and the patch path are in `client.md`. `hsm_sign` reads
    `exp_signature_size` and accepts only 64; `ele_client` ignores SIGPIPE.
  - Resume 3 (verify-1 of 162-skh-main, sibling lane 162-skh-iso): every
    key-store update fails closed until the owner answers Q2 (the ELE
    rollback gap): `ele_delete_key` succeeds only with the counter
    acknowledgement, which the binding never gives, so a delete exits 1 with
    "NOT rollback-protected" like generate; the key-store open, the one vendor
    call that marshals the nonce, runs in a forked child (non-dumpable,
    locked, `_exit`, result over a pipe, parent checks status and exact
    length, erases its nonce right after the fork); the in-process stack
    scrub stays as defence in depth and is not claimed as erasure. Tests: the
    double returns `HSM_NO_ERROR` on delete; a different pid; killed, nonzero
    and short child fail closed; the parent's nonce buffer is zero.
  - Source-level second-reader review of the pinned ELE library commit
    463845060a79 needs the digest-verified source supplied offline to the
    reviewer, which the coordinator has raised with the Tenant; until then the
    binding stays provisional. No vendor source is in this repository.
  - Second reader needed. The claims about the library's response decoder
    (success-tagged warning maps to `HSM_NO_ERROR`), its signature output
    (`signature_size` not updated, `exp_signature_size` set) and its credential
    marshalling (the nonce copied into an unwiped stack buffer) rest on the
    source trace in `client.md` at `ELE_COMMIT` and have had no reader with the
    pinned source. To reproduce the trace: `scripts/ele-lib-build.sh --src-only
    --work <dir outside the checkout>`; it fetches the commit and refuses unless
    the `git archive` tar has SHA-256
    `31f7baedab12e5c5b1efe088d609243e63e5992bea9701082f0942fc4c90c079`
    (`ELE_ARCHIVE_SHA256` in `ele-lib.lock`); then read the file:line cited in
    the contract table. The source is not copied into this repository.
