# Plan: #140 ftpm image build (configuration only)


Row branch `row/140-ftpm-image`. Provisional: the SPEC row `ftpm` is proposed, pending owner approval, and the
open questions in [docs/ftpm/README.md](../ftpm/README.md) stay open.

## Objective

Put the firmware TPM into the platform image as Yocto configuration: kernel driver, OP-TEE with the fTPM early TA,
tpm2-tools in the debug image. Nothing is built with bitbake in this row; the recipes are parsed and the TA source fetched (slice 4).

## Provisional defaults (the owner has not answered)

- NV storage on OP-TEE REE FS. RPMB off (`CFG_RPMB_FS=n`); no RPMB key is programmed, scripted or enabled.
  Limits: no rollback protection, NV lost on a rootfs reflash.
- TA: `optee_ftpm` 4.10.0 on `ms-tpm-20-ref`, pins as in docs/secure-world/build.md, an early TA.
- Kernel: `CONFIG_TCG_TPM=y`, `CONFIG_TCG_FTPM_TEE=y`, so `/dev/tpmrm0` exists once `tee-supplicant` runs.
- tpm2-tools in the debug image only.
- EK template not chosen in the image; the EK is created at first boot by provisioning.

## Slices

1. Kernel fragment `ftpm.cfg`, listed in the bbappend; both symbols in `kernel-required.txt`.
   Test: `test/platform_image_kernel_test.sh` checks them against `ftpm.cfg` and the bbappend naming it.
2. OP-TEE bbappend and an `optee-ftpm` recipe at the pinned revisions; REE FS, RPMB off, early TA.
   Test: a platform-image test that the pins match docs/secure-world/build.md and no RPMB key option exists.
3. tpm2-tools in the debug image; `docs/ftpm/build.md`; links from docs/ftpm/README.md and
   docs/platform-image/build.md. Every measured-boot gap stays listed.

4. Build-host parse (lane 140-ftpm-parse): `make platform-image-parse` passes with the fTPM recipes (meta-tpm joins
   the layers for tpm2-tools; the recipe drops `S`, takes the real license checksum). Docs record the result.
5. Compile (lane 140-ftpm-compile): `bitbake optee-ftpm` and `bitbake optee-os` pass (the TA's make arguments gain
   `LIBGCC_LOCATE_CFLAGS`; only the stripped ELF is built, so no signing key is used); `make platform-image-kernel-config`
   passes with `ftpm.cfg`; the debug image build is attempted. Docs record each command and exit status.
6. Codex P1s: the PKCS#11 early TA beside the fTPM one; the BSP's `optee-client` with `tee-supplicant` enabled at boot;
   a persistent `/data` partition (own wks, GPT name `tee-data`) for its REE-FS storage, mounted before the supplicant;
   the EULA not accepted (`imx-boot` dropped from `WKS_FILE_DEPENDS`). Tests: `test/platform_image_ftpm_test.sh`.
7. Codex P1s, round 2: the wks keeps the BSP's boot partition (kernel, DTBs) and drops only the raw `imx-boot` entry;
   the tee-nv recipe installs `/data`; the NV is wiped with a rootfs reflash, as SPEC row 34 says.
   SPEC row 34 change proposed, pending owner approval (only if NV that survives a rootfs reflash is wanted).
8. Codex security P1 (verify 4): a rootfs-only reflash kept `/data/tee`, against SPEC row 34. Fix in the image: the
   rootfs carries a build identity, and `tee-nv-wipe.service` (before and required by `tee-supplicant`) wipes `/data/tee`
   when `/data/tee-rootfs-id` is missing or differs; it fails closed. The test runs the script on a temp tree. Residual:
   a reflash of the very same build is not told apart.
9. Codex P1s from verify 5, all three fixed:
   - Ordering cycle: the BSP `tee-supplicant@.service` is `DefaultDependencies=no`, `Before=sysinit.target`; the wipe unit
     had the default dependencies (After=sysinit.target) and closed a cycle. It is now `DefaultDependencies=no`, with
     `RequiresMountsFor=/data`, `Before=tee-supplicant@teepriv0.service` and `Conflicts`/`Before=shutdown.target`.
     `systemd-analyze verify` against the built rootfs reports no cycle (command and output in the lane report).
   - Unreadable marker: the saved id is read in its own checked assignment. Absent: wipe. Present but unreadable:
     exit non-zero, `/data/tee` untouched. Test cases: a directory as marker, and mode 000 when not root.
   - Same-image reflash (security): the erasure is coupled to the flashing. `scripts/flash-rootfs.sh` is the only
     supported way to rewrite the root partition: it finds `root` and `tee-data` by GPT name, erases `tee-data`, then writes
     the rootfs, and refuses with nothing written if it cannot find both. It erases first, so an interrupted run never leaves
     a new rootfs beside the old NV. `test/flash_rootfs_test.sh` runs it on regular-file GPT images with a stub `mkfs.ext4`.
     The boot-time identity check stays as the second barrier. A raw root write outside the script is unsupported and keeps
     the NV.

10. Codex round-2 P1 on #158: dropping `imx-boot` removed the image's path to `optee-os`, so a clean image build could
    succeed without the firmware that holds the fTPM. The image recipe now has `do_image_complete[depends] += "optee-os:do_deploy"`;
    `optee-os` already depends on `optee-ftpm:do_deploy`. The task graph (`bitbake -g`) shows both edges.

11. Codex P1s from verify 6:
    - Security: `scripts/flash-rootfs.sh` took partition names from the GPT and split them in the shell, so a name such as
      `tee-data 0 1048576` could inject offsets. The Python reader now matches the exact names `root` and `tee-data` itself and
      prints four validated integers (in-disk, non-overlapping); a duplicate, missing, whitespace or control-character name is
      refused with nothing written. Tests cover a name with spaces and numbers, a newline, a tab, and a duplicate `tee-data`
      or `root`.
    - Reproducibility: the rootfs id embedded `DATETIME`. It is now the SHA-256 of the rootfs tree (paths, types, modes, link
      targets and file contents, less the id file), so identical inputs give identical bytes; the test asserts no clock variable.
